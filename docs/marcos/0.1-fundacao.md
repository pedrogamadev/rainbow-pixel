# Marco 0.1: Fundação

## Contexto

Leia antes de começar: `AGENTS.md` e `docs/rainbow-pixel-escopo-1.0.md`. Este arquivo cobre somente o marco 0.1. Não implementar gameplay, movimento, mapa, tiro, destruição ou renderização de jogo.

## Objetivo

Entregar a base do monorepo com autenticação por e-mail e senha, criação de perfil com nickname, criação e entrada em sala por código, lobby com os jogadores conectados, bots no lobby (sem comportamento), banco com o schema completo da 1.0, CI aplicando migrations de verdade e as ferramentas de teste do marco 0.1 (seed de contas e sessão por aba), conforme as seções 16 e 17 do escopo.

## Restrições técnicas

- pnpm workspaces, Node.js 24 LTS, TypeScript strict em todos os pacotes, com `tsconfig.base.json` compartilhado.
- Servidor: Colyseus (versão estável mais recente, usando a API documentada dessa versão) sobre Express, no mesmo processo e na mesma porta.
- Prisma (versão estável atual), seguindo a forma de configuração de datasource documentada para essa versão. Usar URL com pooler do Supabase para runtime e URL direta para migrations.
- Supabase Auth com e-mail e senha. O cliente usa `@supabase/supabase-js`.
- Validação de JWT no servidor com a biblioteca `jose`. Suportar os dois modos, escolhidos pela variável `AUTH_JWT_MODE`:
  - `jwks`: chaves assimétricas, via `createRemoteJWKSet` em `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`.
  - `secret`: segredo HS256 legado, via `SUPABASE_JWT_SECRET`.
- Cliente: Vite, React, React Router. PixiJS instalado com apenas um componente placeholder de canvas.
- Validação de entrada da API com zod.
- Testes com Vitest. Lint com ESLint e formatação com Prettier.

## Catálogo (packages/shared/src/catalog)

Cada item tem `id` (string estável), `name`, `enabled` e campos específicos. Exportar tipos derivados dos ids (por exemplo, `WeaponId`).

- modes: `quick` (Partida rápida, enabled true), `unranked` (Sem colocação, enabled false), `ranked` (Ranqueada, enabled false).
- operators: `recruit` (Recruta, enabled true). `weaponIds` contém todas as armas. `gadgetIds` por lado: ataque `breach_charge` e `drone`; defesa `reinforcement` e `barricade`.
- weapons: valores das seções 5.1 e 5.2 do escopo. Campos: `id`, `name`, `slot` (`primary` | `secondary`), `category`, `damage`, `pellets` (1, exceto M870 com 8), `rpm`, `fireMode` (`auto` | `semi` | `pump`), `magazine`, `reloadMs`, `rangePx`, `penetrationCells`, `mobility`, `enabled`.
  - Primárias: M4A1, MP5, M870, M249, SR-25.
  - Secundárias: M9, .357 Magnum, Skorpion vz. 61.
  - Ids em kebab-case: `m4a1`, `mp5`, `m870`, `m249`, `sr-25`, `m9`, `magnum-357`, `skorpion-vz61`.
- gadgets: `breach_charge`, `drone`, `reinforcement`, `barricade`, com `side`, `quantity` e `quantityScope` (`player` | `team`), conforme seção 6 do escopo.
- botDifficulties: `easy` (Fácil), `medium` (Médio), `hard` (Difícil). Os parâmetros da seção 16.4 do escopo ficam em `packages/shared/src/config` (`reactionMs`, `aimErrorDeg`, `turnSpeedDegPerSec`, `maxBurst`, `soundAttention`, `memoryMs`), mesmo que ainda não sejam usados neste marco.

## Banco de dados

Implementar exatamente os models e enums da seção 11 do escopo: `Side`, `RoundEndReason`, `Profile`, `PlayerStats`, `Loadout`, `Match`, `MatchPlayer`, `MatchRound`. `Profile.id` é igual ao id do usuário no Supabase Auth. Gerar a migration inicial e versioná-la.

Unicidade de nickname sem diferenciar maiúsculas de minúsculas: adicionar coluna `nicknameLower` única (ou índice único sobre `lower(nickname)` via SQL na migration). Escolher uma abordagem e documentar no resumo final.

## API REST (apps/server/src/http)

Todas as rotas, exceto `/health`, exigem o header `Authorization: Bearer <jwt do Supabase>`.

| Método e rota | Comportamento |
|---|---|
| `GET /health` | 200 `{ "status": "ok" }` |
| `GET /me` | 200 com o Profile do usuário autenticado; 404 se o perfil ainda não existir |
| `POST /profiles` | Corpo `{ "nickname": string }`. Cria Profile e PlayerStats zerado. 400 se o nickname for inválido; 409 se o nickname existir; 409 se o usuário já tiver perfil |

Regra de nickname (implementada em `packages/shared/src/validation/nickname.ts` e reutilizada no cliente e no servidor): 3 a 16 caracteres, regex `^[A-Za-z0-9_]+$`.

CORS liberado somente para as origens em `CORS_ORIGINS` (lista separada por vírgula).

## Sala Colyseus: QuickMatchRoom

- Nome registrado: `quick_match`. `maxClients = 4`.
- Código da sala: 6 caracteres do alfabeto `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, gerado no `onCreate` e atribuído ao `roomId`, com verificação de colisão contra salas ativas.
- `onAuth`: valida o JWT, carrega o Profile pelo id do token e rejeita se o token for inválido ou o perfil não existir. O mesmo usuário não pode ocupar duas vagas na mesma sala.
- Estado sincronizado: `players` (mapa por `playerId`) com `kind` (`human` | `bot`), `profileId` (vazio para bot), `nickname`, `team` (0 ou 1, no máximo 2 por time contando humanos e bots), `ready` (boolean), `connected` (boolean) e `botDifficulty` (vazio para humano). Para humano, `playerId` é o sessionId; para bot, `bot:<n>`. Campo `code` com o código da sala. Campo `hostSessionId`.
- Mensagem `toggle_ready` alterna o `ready` do próprio jogador humano.

### Bots no lobby (seção 16.2 do escopo)

- Mensagem `add_bot { team, difficulty }`: somente o host. Adiciona bot no time indicado se houver vaga nesse time. Recusa se a sala já tiver 3 bots ou 4 jogadores no total.
- Mensagem `remove_bot { playerId }`: somente o host.
- Bot está sempre `ready = true` e `connected = true`.
- Nome do bot: `BOT <Dificuldade> <n>`, por exemplo `BOT Médio 2`.
- A sala precisa de pelo menos 1 humano. Se o último humano sair, a sala é descartada com os bots.
- Humano que entra quando humanos + bots = 4 substitui o bot adicionado por último (o bot é removido antes de o humano receber vaga e time). `maxClients = 4` continua limitando apenas humanos.
- Toda a lógica de vagas, times e bots fica em `rooms/lobbySlots.ts` como funções puras, para teste unitário.
- Bot não tem comportamento neste marco: ele só existe no estado da sala.
- Reconexão: permitir que o mesmo usuário reconecte por até 60 segundos (seção 3.1 do escopo). Durante a espera, o jogador continua na lista marcado como desconectado.
- Ao sair definitivamente, o jogador é removido. Se o host sair, o próximo jogador vira host. Sala vazia é descartada.
- Nenhuma lógica de partida neste marco. Quando os 4 jogadores estiverem prontos, apenas registrar em log que a partida poderia começar.

## Cliente

- Fluxo: Login ou Cadastro -> `GET /me` -> se 404, tela CreateProfile -> Home (botões "Criar sala" e "Entrar com código") -> Lobby.
- Lobby: código da sala em destaque com botão de copiar, jogadores separados por time com estado de pronto e de conexão, botão "Pronto" e botão "Sair".
- Bots aparecem com a tag BOT. Para o host, cada vaga vazia mostra "Adicionar bot" com seletor de dificuldade, e cada bot mostra "Remover".
- O token do Supabase é enviado no header da API e nas opções de entrada da sala.
- Ao recarregar a página dentro do lobby, tentar reconectar na mesma sala usando o token de reconexão do Colyseus salvo em sessionStorage.
- Interface simples e funcional. Sem trabalho de design neste marco.

## Ferramentas de teste do marco 0.1 (seção 17 do escopo)

- Todas atrás de `DEV_TOOLS=true` no servidor e `VITE_DEV_TOOLS=true` no cliente.
- `dev/guard.ts`: o servidor encerra na inicialização com erro claro se `DEV_TOOLS=true` e `NODE_ENV=production`.
- Seed de contas: script `pnpm dev:seed-users` cria (ou mantém, se já existirem) 4 usuários `dev1@rainbowpixel.local` a `dev4@rainbowpixel.local` com a senha de `DEV_SEED_PASSWORD`, já confirmados, e os perfis `dev1` a `dev4`. Usa a API administrativa do Supabase com `SUPABASE_SECRET_KEY`, que existe só no servidor e nunca no cliente. O script é idempotente e se recusa a rodar sem `DEV_TOOLS=true`.
- Sessão por aba: com `VITE_DEV_TOOLS=true`, o cliente Supabase usa `sessionStorage` como armazenamento de sessão, para cada aba ficar logada numa conta diferente. Sem a flag, usa o padrão.
- Na tela de login, com `VITE_DEV_TOOLS=true`, mostrar botões de acesso rápido "Entrar como dev1" a "dev4".

## CI (.github/workflows/ci.yml)

Em push e pull request:

1. Checkout, setup de pnpm e Node 24 com cache.
2. `pnpm install --frozen-lockfile`.
3. `pnpm lint`.
4. `pnpm typecheck`.
5. `pnpm test`.
6. Subir serviço PostgreSQL 16 no próprio workflow e executar `prisma migrate deploy` contra ele. O pipeline deve falhar se a migration falhar. É proibido pular este passo ou torná-lo condicional.
7. `pnpm build`.

## Testes mínimos

- `nickname.ts`: válidos, curtos, longos, caracteres inválidos, espaços.
- `roomCode.ts`: tamanho, alfabeto permitido, ausência de caracteres ambíguos.
- Catálogo: ids únicos em cada catálogo; apenas `quick` habilitado em modes; apenas `recruit` em operators; 5 armas `primary` e 3 `secondary`; todo `weaponId` e `gadgetId` do operador existe no catálogo.
- `verifyJwt`: token válido, expirado, assinatura inválida (usar chave gerada no teste, sem rede).
- `lobbySlots.ts`: nunca mais de 2 jogadores por time; no máximo 3 bots; somente o host adiciona e remove bot; humano entrando em sala cheia substitui o último bot; sala sem humano é descartada.
- `dev/guard.ts`: recusa `DEV_TOOLS=true` com `NODE_ENV=production`.

## Critérios de aceite

1. `pnpm install`, `pnpm lint`, `pnpm typecheck`, `pnpm test` e `pnpm build` passam do zero em máquina limpa.
2. CI verde no GitHub, com o passo de migration executado contra o PostgreSQL do workflow.
3. Um usuário cria conta, cria perfil com nickname e chega na Home.
4. Nickname duplicado (inclusive com maiúsculas diferentes) é recusado com mensagem clara.
5. Um usuário cria sala e recebe um código de 6 caracteres; outro usuário entra pelo código e os dois se veem no lobby, em times distribuídos.
6. Recarregar a página no lobby reconecta o jogador na mesma sala em até 60 segundos.
7. Dois usuários em redes diferentes entram na mesma sala com o servidor exposto por Cloudflare Tunnel.
8. Nenhum segredo commitado; `.env.example` completo nos dois apps.
9. Sozinho: `pnpm dev:seed-users` cria as 4 contas; em 4 abas do mesmo navegador, cada uma logada numa conta, os 4 entram na mesma sala e o lobby fecha 2v2.
10. O host adiciona 3 bots com dificuldades diferentes e o lobby fica 4/4; remove um bot e a vaga volta a ficar livre.
11. Com a sala cheia (1 humano e 3 bots), outro humano entra pelo código e substitui o último bot.
12. O servidor não inicia com `DEV_TOOLS=true` e `NODE_ENV=production`.
